# Safety Model — SynapseOps

> **Foundational principle**: SynapseOps is designed so that AI reasoning and action execution are architecturally separated. The system's intelligence can be as sophisticated as needed. The boundary between intelligence and execution is governed by deterministic policy and authorization logic that AI components cannot bypass.

---

## 1. Why Safety is Architecturally Fundamental

Infrastructure operations involve real systems running real workloads. An incorrect autonomous action can:

- Cause a service outage
- Trigger a cascading failure
- Corrupt data
- Degrade system performance
- Create security vulnerabilities
- Cause financial impact

An autonomous system that can act on infrastructure without appropriate constraints is more dangerous than a system that does nothing. Safety is therefore not a feature to be added later — it is an architectural principle embedded from the beginning.

The goal is not to prevent autonomy. The goal is to ensure that **autonomy is always bounded, auditable, and governable**.

---

## 2. The Safety Architecture

Every proposed action flows through the following deterministic stages before any execution occurs:

```
OBSERVATION
    ↓
ANALYSIS (ML / AI reasoning)
    ↓
PROPOSAL (structured action candidate)
    ↓
SCHEMA VALIDATION (Pydantic validation)
    ↓
PRECONDITION CHECK (is the action applicable to current state?)
    ↓
POLICY EVALUATION (is this action permitted by defined rules?)
    ↓
RISK CLASSIFICATION (what risk level does this action carry?)
    ↓
AUTHORIZATION (is this risk level autonomously authorized?)
    ├── YES → proceed to execution
    └── NO → route to Human Approval Queue
           ↓
    HUMAN DECISION
           ↓
EXECUTION (bounded action executor)
    ↓
VERIFICATION (did the system recover?)
    ↓
AUDIT LOG (unconditional record of all decisions and outcomes)
```

Every stage is deterministic except the analysis stage. The LLM or ML output enters the pipeline at the Proposal stage and cannot proceed to Execution without passing through all subsequent deterministic checks.

---

## 3. Action Risk Classification

SynapseOps uses a risk hierarchy to determine how proposed actions are authorized.

| Risk Level | Characteristics | Authorization Model |
|---|---|---|
| **LOW** | Reversible, bounded scope, high historical success rate, low blast radius, high-confidence diagnosis | Potentially eligible for autonomous execution under strict policy conditions |
| **MEDIUM** | Partially reversible, moderate scope, moderate confidence, standard service impact | Potentially eligible for autonomous execution under stricter conditions; may require additional confirmation |
| **HIGH** | Limited reversibility, broad scope, lower confidence, critical service impact, first-time action type | Requires explicit human authorization |
| **CRITICAL / DESTRUCTIVE** | Irreversible, data-modifying, system-wide impact, or security-affecting | Must not be autonomously executed; requires specifically designed authorization protocol |

**Important**: These categories are conceptual at Phase 0. Exact risk scoring criteria, the risk scoring function, and autonomous action eligibility rules will be specified in Phase 9 (Safety / Policy / Human Approval).

## 4. Fundamental Safety Principles

### 4.1 No Arbitrary Command Execution

The system must never execute arbitrary shell commands, scripts, or free-form instructions generated by an AI component. All executable actions must conform to a defined, bounded action schema.

```
❌  LLM generates: "Run: kubectl delete pod --all"
✅  LLM generates: {"action_type": "restart_service", "target": "worker", "scope": "single_instance"}
    → Validated → Policy check → Authorized → Executed via bounded executor
```

### 4.2 Least Privilege

The action executor holds only the minimum infrastructure permissions required for the defined action set. It does not hold admin or root credentials. Each permission is explicitly scoped to its intended purpose.

### 4.3 Bounded Actions

All executable actions have defined boundaries:
- **Target scope**: Which service, container, or resource is affected
- **Maximum blast radius**: How broadly the action can affect the system
- **Timeout**: Maximum duration after which the action is abandoned and an error is logged
- **Rollback availability**: Whether the action can be undone if unsuccessful

### 4.4 Dry-Run Mode

Before any new action type is enabled for autonomous execution, it must first be validated in dry-run mode, where the action is simulated but not executed. Dry-run results are logged and reviewed before production enablement.

### 4.5 Simulation Mode

SynapseOps must support a full simulation mode where the entire operational loop runs against the simulated infrastructure. Real infrastructure execution is only enabled in explicitly configured environments.

### 4.6 Rollback Strategy

Wherever technically feasible, recovery actions should have a defined rollback procedure. If an executed action worsens the situation or verification fails, the rollback should be automatically triggered (subject to its own risk classification and authorization).

### 4.7 Rate Limiting

The system must enforce limits on:
- Actions per time window on a single service
- Total actions across the system per time window
- Repeated actions of the same type on the same target (circuit-breaker pattern)

This prevents runaway action loops if verification is incorrectly triggering further action cycles.

### 4.8 Audit Logging

Every action-related decision is unconditionally logged, regardless of outcome:

| Event | Logged |
|---|---|
| Anomaly detected | ✅ |
| Incident created | ✅ |
| Hypothesis generated | ✅ |
| Recovery plan proposed | ✅ |
| Policy decision (authorized/denied/escalated) | ✅ |
| Human approval requested | ✅ |
| Human approval granted/denied | ✅ |
| Action executed | ✅ |
| Action outcome | ✅ |
| Verification result | ✅ |
| Rollback triggered | ✅ |

Audit logs must be append-only and must not be modifiable by AI components.

### 4.9 Human Override

Human operators must always be able to:
- Cancel a pending autonomous action before execution
- Override an AI-generated recommendation with a manual action
- Correct an AI-generated hypothesis or diagnosis
- Pause or disable autonomous action execution entirely
- Review all pending, active, and historical decisions

---

## 5. The Human Approval Layer

High-risk and critical actions route to the human approval queue rather than executing autonomously. When a human approval request is generated, the operator receives:

| Information | Purpose |
|---|---|
| Incident summary | What was detected |
| Observed evidence | The specific telemetry that triggered the incident |
| Root cause hypothesis | What the system believes is the cause, with confidence |
| Proposed action | What the system wants to execute |
| Risk classification | Why this action requires human approval |
| Expected outcome | What recovery the system expects the action to achieve |
| Alternative actions | Other options the system considered |
| Rollback plan | How the action can be undone if it fails |

The operator can: **Approve**, **Deny**, **Request modification**, or **Dismiss the incident**.

---

## 6. Failure Containment

The system must be designed so that failures within SynapseOps itself do not cause infrastructure harm:

| SynapseOps Failure Mode | Expected Behavior |
|---|---|
| LLM API unavailable | Fall back to human escalation or simpler deterministic diagnosis |
| Anomaly detection model fails | Fall back to threshold-based alerting |
| Policy engine fails | Block all autonomous actions until policy engine is restored |
| Database unavailable | Continue observing; pause action execution |
| Action executor fails | Log failure; escalate to human; do not retry autonomously without new authorization |
| Network connectivity lost | Degrade gracefully; alert operators; do not fail silently |

---

## 7. What Will Be Defined in Phase 9

The Phase 9 Safety / Policy / Human Approval implementation will specify:

- Exact risk scoring criteria and scoring function
- The complete policy rule set (initial version)
- Specific action types and their default risk levels
- Authorization thresholds for autonomous execution
- Human approval UI design
- Audit log format and storage
- Rate limiting parameters
- Circuit-breaker thresholds

Phase 0 defines the architecture and principles. Phase 9 defines the implementation. This separation ensures that safety policy is not written casually as a byproduct of implementation, but designed deliberately as a first-class engineering effort.

---

## 8. Safety as an Ongoing Practice

Safety is not a phase with a completion date. Every future phase must review:

- Does this new component introduce new execution pathways that bypass the policy layer?
- Does this new component request permissions beyond what its responsibilities require?
- Does this new component have deterministic failure modes or does it fail silently?
- Does this new component's output reach the executor without passing through validation?

Safety review must be part of every phase completion check.
